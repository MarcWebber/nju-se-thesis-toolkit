# 协作问题排查

当用户指出协作或交付中已经出现的问题时，助手使用这个 Skill 找出原因、完成修复，并向用户说明哪些结果已经核验、哪些效果需要读者评价。局部问题可以直接处理：助手读取对应指引中的相关一节，修改出问题的位置，然后报告结果。

## 定位问题

助手把三类信息分开对待：用户的要求、现有事实和自己的推断。用户的要求以原话为准，多次要求互相冲突时，最新的明确要求优先。现有事实来自文件内容、原始输出和运行记录。推断只是待验证的假设，助手在材料中核实之后才把它当作结论使用。

助手根据下表选读指引，只读与当前症状对应的部分。多个症状同时出现时，助手先处理最妨碍用户目标的一项，并在回复中列出其余症状。

| 用户反馈或现象 | 问题 | 指引 |
|---|---|---|
| 用户要求产出回到自己的原话，或助手的推测被写成了既定事实。 | 过早定调 | [理解与范围](references/understanding-and-scope.md#过早定调) |
| 用户希望交付更精简，或简单任务多出了流程、脚本和文件。 | 过度设计 | [理解与范围](references/understanding-and-scope.md#过度设计) |
| 交接说明限定了标题、段数和顺序，写作者的产出读起来像在填表。 | 过度约束 | [理解与范围](references/understanding-and-scope.md#过度约束) |
| 通用说明里出现了某个项目的事实或某位用户的偏好。 | 个案固化 | [理解与范围](references/understanding-and-scope.md#个案固化) |
| 评审者或协调者改写了正文，或整理者交出了成稿。 | 职责混淆 | [角色与来源](references/roles-and-sources.md#职责混淆) |
| 协作各方对最终稿说法各异，或成稿的实际执行者与用户指定的执行者存在出入。 | 来源和版本混乱 | [角色与来源](references/roles-and-sources.md#来源和版本混乱) |
| 读者需要反复回翻才能找到前提，或比较对象所处的条件各异。 | 层次混杂 | [表达与图示](references/expression-and-diagrams.md#层次混杂) |
| 读者对标题或句子感到费解，需要反复阅读才能复述其意思。 | 表达拥挤 | [表达与图示](references/expression-and-diagrams.md#表达拥挤) |
| 图示与实际关系存在出入，箭头含义模糊，或显示出现重叠和裁切。 | 图示模板化 | [表达与图示](references/expression-and-diagrams.md#图示模板化) |
| 面向读者的正文里夹杂着仅服务于制作过程的记录。 | 过程信息侵入成品 | [表达与图示](references/expression-and-diagrams.md#过程信息侵入成品) |
| 交付物通过了数量或程序检查，用户目标仍有缺口。 | 验收偏移 | [验收与结果说明](references/acceptance.md#验收偏移) |

## 修复问题

### 在已有授权内执行

助手依据当前会话中仍然有效的授权和用户最新的选择，确定由谁修改哪些内容。用户已经提出修复要求时，助手在这一范围内直接执行。资料缺口会改变修复方向时，例如两种理解会导向截然有别的交付物，助手向用户提出一个具体问题，说明需要哪项资料、它影响哪种选择。其余情况下，助手依据现有材料作出判断，并在回复中说明依据。

### 让方法与问题规模相称

助手按问题的实际范围安排修改。一个标题或一句话出错时，助手只改这一处；一整节或一份交付物偏离要求时，助手在这一节或这份交付物的范围内重组。修复使用项目现有的工具、目录和格式；用户目标确实需要时，助手才新增脚本、文件或流程。

### 保护用户当前成果

助手以用户当前的文件状态为起点。`git status` 和 `git diff` 能显示哪些文件和行发生了变化，助手用它们限定修改范围。判断某段内容出自谁时，助手查阅已有的原始记录，例如会话记录、子代理或外部模型的原始输出、提交记录中的作者与说明，以及用户的明确陈述。记录只能提供部分线索时，助手把这段内容当作用户当前成果保留，并在回复中说明出处仍待确认。撤回多余产出之前，助手先检查其他文件和会话是否引用了它。

## 角色与职责

整理者提供用户要求、资料事实、出处和硬性约束。写作者负责成品的结构与表达，并决定如何处理评审建议。评审者指出问题，给出依据和建议方向；评审者始终以建议的形式交付，正文修订由授权写作者或用户实施。协调者核对事实，原样落盘写作者的文本，并运行验证。

其他职责按当前任务的授权分配和执行。

## 报告结果

助手在回复中说明偏差是什么、原因是什么、改了哪些内容，并把结果分成两类陈述。客观核验是对照材料或运行检查就能得出结论的内容，例如事实与原文一致、链接有效、撤回的文件已离开交付位置、测试通过；助手写明检查方法和结果，并逐项列出尚待执行的检查。主观效果是需要读者评价的内容，例如是否易读、结构是否顺畅、图示是否直观；助手说明做了哪些调整、预期改善什么，由读者在实际使用中判断。详细做法见 [验收与结果说明](references/acceptance.md#报告修复结果)。

## 沉淀经验

需要沉淀经验时，助手先检验：换一个项目、换一位用户，这条经验还成立吗？跨项目成立的协作经验写入本 Skill 或项目的通用复盘文档，领域方法写入对应领域 Skill 的 references，项目事实与个人偏好保存在工作区的本地知识资料中。
