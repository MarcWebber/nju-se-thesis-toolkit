# 章节写作

配合 [共用规则](../SKILL.md#共用规则) 使用。

## 1. 输入

```text
操作：起草 / 续写 / 修改
目标章节与前后文：
本节问题：
事实材料与来源：
保留的术语、数字和引用键：
参考范文及希望借鉴的特点：
输出位置与形式：
```

## 2. 各章重点

沿用作者模板，只使用与本次任务有关的条目。下表是工程论文的内容分工建议，不是固定目录。

| 内容 | 要写清什么 |
|---|---|
| 绪论 | 具体场景、现有处理方式的限制、本文工作及作者贡献 |
| 需求分析 | 参与者、系统边界、正常与异常场景、可观察的验收条件 |
| 系统设计 | 目标约束、总体方案、关键取舍与代价；数据关系和接口语义 |
| 系统实现 | 关键机制的触发条件、处理对象、动作和结果 |
| 系统验证 | 验证问题、环境、方法、指标定义、实际结果及解释 |
| 总结 | 对论文问题的回应、完成的工作、实际限制与后续方向 |
| 摘要 | 主体已有的问题、工作与结果；中英文事实及结论范围一致 |

## 3. 起草与修改

1. 确定本节要解释的关系，例如约束为何导致某项设计、一次操作如何改变数据、结果支持什么判断。围绕这些关系安排段落。
2. 设计写选择依据，实现写实际行为。模块名称、字段字典和函数调用清单本身不能代替机制说明。
3. 并发机制说明共享数据和原子操作边界；异步机制说明发送、提交、确认与重试的顺序。代码分析方法见 [代码与工程图表](writing-engineering.md)。
4. 验证段先报告观察，再解释原因。环境、负载、指标和计算口径应足以复核；区分功能场景结果与性能测量。
5. 参考范文只用于校准术语、引证方式、段落展开和图后分析，不搬用其中的项目事实。
6. 修改已有稿件时，先解决具体问题：跳步、歧义、重复、事实冲突或证据错配。未出问题的内容保留。

## 4. 表达

1. 句子说清谁对什么做了什么。用实际动作替代“进行相关处理”“实现显著提升”等空泛描述。
2. 同一概念使用同一术语。保留影响结论的条件，删去没有依据的评价词。
3. 按论证关系分段，不固定每段句数、句序或长短。比较维度多时用表，交互顺序难说明时用图。
4. 合并承担同一论证任务的段落。过渡句和小结只在确有承接需要时使用。
5. 图后解释读者需要注意的关系或结果，不逐项复述所有图元或数值。

## 5. Example

以下为合成案例。

给定事实：

1. 服务用 request_id 标识请求，数据库为该字段设置唯一约束。
2. 请求记录插入与业务对象更新处于同一事务。
3. 唯一约束冲突时读取已有结果并返回。

原稿：系统采用先进的幂等设计，极大提升了稳定性，保证任何情况下都不会重复处理。

改写：

服务通过 request_id 识别重复请求。请求记录与业务更新在同一数据库事务中提交；唯一约束冲突时，服务读取已有结果并返回。该机制约束事务内的业务更新，不覆盖事务外的消息发送。

修订依据：原材料给出了事务内去重机制，没有提供稳定性提升数据，也没有支持“任何情况下”的保证。
